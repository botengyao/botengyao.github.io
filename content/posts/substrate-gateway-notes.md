*Method note, up front, because it changes how you should read this. I did not read `atenet` line by line. I pointed an AI agent at Agent Substrate's networking code and had it read the whole thing in seven passes, each with a different question, then had a second round of agents try to refute everything the first round produced. Eight findings did not survive that; four of them are quoted at the bottom. Every citation below resolves to a file and line at a named commit, which is the only reason a list produced this way is worth publishing: you can check any of it yourself, and I would rather you did than take it on trust.*

Agent Substrate multiplexes many agent "actors" onto a smaller pool of already-warm worker pods, which is the whole trick: it keeps the Kubernetes control plane out of the request path so a request can reach a suspended agent in milliseconds rather than seconds. `atenet` is the part that gets traffic there. It is an Envoy xDS control plane, an ext_proc server that resolves which worker currently holds a given actor and resumes it if nobody does, and a second gateway on the way back out that authenticates the actor behind every outbound `CONNECT`.

It is a genuinely good piece of engineering, and the comments in it are unusually honest — several of the items below are things the code already says about itself in a `TODO`. What follows is the engineering half of what the scan turned up: 52 items about correctness, capacity, operations, observability, and test coverage.

There is a security half too. It is not in this post. The repo ships a [`SECURITY.md`](https://github.com/agent-substrate/substrate/blob/main/.github/SECURITY.md) asking for private reports through GitHub advisories and asking reporters to hold details until a fix lands, and it seemed poor form to read that file and then ignore it. Those findings are going through that channel. If they get advisories, I'll write them up then.

## The line that was never backported

Substrate ships two egress manifests. `atenet-egress.yaml` is the default; `atenet-egress-with-sdsmint.yaml` is the variant that terminates and re-originates TLS so it can see inside the tunnel. They are siblings, and they drifted.

The sdsmint one sets this on its `CONNECT` route:

```yaml
- match: { connect_matcher: {} }
  route:
    cluster: mitm_internal
    # Set request timeout to disabled (0) as CONNECT is a long-running stream.
    # There will still be a stream_idle_timeout (5 minutes by default).
    timeout: 0s
```

The default one does not:

```yaml
- match: { connect_matcher: {} }
  route:
    cluster: egress_forward_proxy
    upgrade_configs:
    - upgrade_type: CONNECT
      connect_config: {}
```

Envoy applies the route timeout to a `CONNECT` tunnel's entire lifetime, not just to its headers. Left at the 15-second default, that is not a timeout on a slow request — it is a hard cap on how long any actor's outbound connection may exist. Server-sent events, gRPC streaming, an SSH session, a slow model call, any download over fifteen seconds: all cut, mid-stream, on the default install path.

The router's own xDS code gets this right for the *ingress* `CONNECT` listener, and says why:

```go
// Envoy applies the route timeout to a CONNECT tunnel's whole
// lifetime, not just its headers; left at Envoy's 15s default
// this would silently kill every tunnel after 15s. 0 disables
// it -- the tunnel's lifetime is bounded by idle timeout,
// drain, and the peers themselves.
Timeout: durationpb.New(0),
```

So the knowledge is in the tree three times — twice in prose, once in Go — and missing from the one file `hack/install-ate.sh` actually applies. This is the cheapest fix on the list and the one I would do first. The durable version of it is an end-to-end test that holds a tunnel open past twenty seconds and asserts bytes still flow, so the two manifests cannot drift apart again quietly.

This is also the kind of finding the method is genuinely good at. Nobody reading either file alone would notice; the bug exists only in the diff between two files nobody diffs.

## A reconcile that lists, then throws it away

The router keeps Envoy configured through a loop that ticks every five seconds:

```go
func (c *Controller) reconcile(ctx context.Context) error {
	_, err := c.atStore.readyTemplates(ctx)
	if err != nil { /* ... */ }
	if err := c.xdsSrv.UpdateSnapshot(); err != nil { /* ... */ }
	return nil
}
```

Two things are happening here, and neither is doing what it looks like.

`readyTemplates` is an unpaginated, cluster-wide `List` of every `ActorTemplate`, and the result is assigned to `_`. It is also not served from an informer cache — the client is built with `client.New`, which is the direct, uncached one — so this is a real API-server round trip. Nothing in the generated xDS resources derives from `ActorTemplate` at all; the only genuine consumer is the `/statusz` page, which does its own fetch.

`UpdateSnapshot` then increments the version counter unconditionally and calls `SetSnapshot`. go-control-plane pushes on a version change, so Envoy re-ingests the full listener, cluster, route and secret set every five seconds, forever, whether or not a single byte differs. On an idle cluster that is roughly seventeen thousand pushes and seventeen thousand "Deploying updated xDS configuration snapshot" log lines per replica per day.

The obvious reason someone might have written it this way is that the periodic push refreshes the TLS material. It doesn't: the secret is delivered as a `DataSource_Filename` with a `WatchedDirectory`, so Envoy re-reads the file on its own when kubelet rotates it. The push is not load-bearing. That check is the kind of thing the verification round is for — the first pass reported the churn, the second pass went looking for the reason it might be deliberate, and not finding one is what makes the finding worth acting on.

The fix is to hash the built resource set and skip the version bump when nothing changed, and to delete the discarded `List`. What makes it worth writing down is the test that goes with it, which is one line of intent: two back-to-back reconciles should produce exactly one `SetSnapshot`.

## The benchmark measures a different gateway

The shipped ingress Deployment starts Envoy like this:

```yaml
- --component-log-level
- upstream:debug,router:debug,ext_proc:debug
```

No comment, no time-box, no overlay that removes it. Those are three of Envoy's hottest components, each emitting several lines per request on the data path, and `ext_proc` debug output puts request headers — actor hostnames included — into cluster logs by default. The egress Envoy, running the same binary, carries no such flag.

The part worth stopping on is in the load-test harness: before it measures anything, `nighthawk_ingress.py` strategic-patches the Envoy container's entire `command` to remove those flags — and documents why, in the docstring of the function that does it. So the harness is honest about measuring something other than the default. What nobody says is the corollary: the configuration that actually ships, debug logging and all, has never been benchmarked, and the manifest carries no note to that effect.

It sits next to two other manifest gaps that read the same way — as things nobody decided, rather than things somebody chose. The ingress Envoy container has no readiness, liveness, or startup probe of any kind, while its egress twin has two; and neither gateway sets resource requests or limits, which puts both in BestEffort QoS, first to be evicted under node pressure. In each case the sibling manifest already demonstrates the intended shape. That is what makes them cheap: there is nothing to design, only something to copy.

## How this was actually produced

Worth being specific, since the method is doing a lot of the work here.

Seven agents read the same surface in parallel, each given a different question: the generated xDS, the ingress request path, the egress path and actor identity, the ext_proc server, the manifests and operational posture, the EgressPolicy API, and performance plus test coverage. Each returned structured findings with file-and-line citations.

Then a second round, and this is the part that matters. Every finding went to a fresh agent whose only instruction was to knock it down — open the cited file, read around the line, and decide whether the code already handles it, whether the failure can actually occur in the deployed topology, or whether the Envoy or Kubernetes default it complains about is quietly fine. That round killed eight of 129 claims and corrected the severity or the reasoning on several more.

The refutations are the most useful output of the whole exercise, so here are four of them — the ones that don't touch the findings I'm holding back:

- **Unbounded ingress buffers and stream idle.** One reviewer claimed <code>per_connection_buffer_limit_bytes</code> and <code>stream_idle_timeout</code> are unbounded on the ingress listeners. Envoy already defaults to 1 MiB and 5 minutes, and <code>max_concurrent_streams</code> defaults to 1024 (not 2<sup>31</sup>). Kept only the genuine gaps: the header-phase <code>request_timeout</code>, the stream cap, and connection lifetime.
- **A goroutine leaks per CONNECT while ateapi is wedged.** Refuted — Envoy's <code>message_timeout</code> reset cancels the server-side stream context. The deadline in 3.9 is still worth adding, for the serial <code>Process</code> loop, not for a leak.
- **<code>codes.Canceled</code> is mismapped to a 500.** Dropped entirely — the claimed trigger (ateapi <code>Stop()</code> during drain) is wrong; grpc-go surfaces that as <code>Unavailable</code>, and nothing in the repo returns <code>Canceled</code>.
- **The egress ext-proc container should be a native sidecar.** Refuted — the ext-proc container has its own readinessProbe, so the pod is not added to Service endpoints until it is listening. The "burst of failures on every pod start" does not happen.

The pattern in all four is the same, and it is the characteristic failure mode of a fast reader, machine or otherwise: a real fact, cited correctly, attached to a consequence that doesn't follow. Defaults are the richest source of it. "No `max_concurrent_streams` is set" is true and sounds alarming; the default is 1024, which is fine. "The Envoy container has no readiness probe" is true, and on a normal rollout the pod still leaves the Service on `deletionTimestamp`, so the thing you were worried about doesn't happen and a different, smaller thing does.

## What I would and would not trust here

An agent reading a codebase is very good at the class of bug that lives in the gap between two files. The `CONNECT` timeout above is the clearest example: two sibling manifests, one line different, and no human reviewer diffs manifests against each other. Same for the discarded `List`, the debug flags the benchmark strips, the probe that exists on one gateway and not its twin. These are all *drift* findings, and drift is exactly what tireless comparison is for.

It is much weaker at intent. It cannot tell you that a limit is unset because someone measured it and decided the default was right, and it will confidently produce a plausible failure mode for a default that has never failed. That is what the refutation round is patching, imperfectly — eight caught out of 129 is a floor on the error rate, not a ceiling.

So: treat the citations as reliable, the reasoning as a strong hypothesis, and the priorities as one outsider's opinion with no production context behind it. The three findings I led with are the ones I am asserting rather than merely reporting: each was re-checked directly against the cited files, not against an agent's summary of them. For the remaining forty-nine, the honest description is that a machine read the code carefully, a second machine argued with it, and I am publishing the transcript because the citations make it checkable.

I would rather publish that with the corrections attached than a cleaner list that quietly dropped them.
